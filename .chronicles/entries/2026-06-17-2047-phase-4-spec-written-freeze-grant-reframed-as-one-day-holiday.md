# 2026-06-17 2047 — Phase 4 deep spec written; the parent "freeze" reframed as a one-day Holiday (no engine change)

Reviewed the Sonnet-built Phase 3a (clean — 38/38, no lingering `settings.html`/`lessonLenMin`, deploy globs both HTML files; only minor non-blocking notes) and then wrote the Phase 4 deep spec (`docs/main-app-phase-4.md`) for a less-powerful agent to implement. Phase 4 is **pure shell**: a PIN-gated parent area (`parent.html` + `parent.js`) whose controls mutate fact arrays and let `project()` re-derive everything. `motivation.js` is explicitly untouched; `npm test` stays 38/38.

**Why:** Phase 4's roadmap outline listed "optionally **grant a freeze**" as a parent control. But the engine persists facts only — `freeze.banked` is *derived* by replay from `regenCount`; there is no freeze-grant input. So that one control, unlike lesson/holiday/floor/rest-weekday (all already honored by the engine), looked like it needed a new engine input + replay + tests, breaking the "engine is done, Phase 4 is UI-only" principle.

**What was decided:** The parent "freeze a day" is modelled as a **one-day Holiday** (`{start: D, end: D}` in `holidays[]`). A parent-declared day that holds the streak *is* the Holiday primitive — §9 checks Holiday before the auto-freeze, excludes it from regen, and lets playing beat it. So "protect days off" (sick day → one day; trip → wider range) is a single control writing `holidays[]`, with **zero engine change**. A bonus falls out of the precedence order: because Holiday is checked before the auto-freeze, declaring a known day off does **not** consume the banked emergency freeze — it stays for a genuine surprise slip.

**Why not a new `freezeGrants[]`/`frozenDays[]` input:** It would (a) reopen the finished engine in a UI-only phase, and (b) add a *second* mechanism that reaches the `Frozen`/held outcome — a fresh "two mechanisms, one job" smell, the inverse of the [[five-non-overloaded-primitives]] invariant. The correct primitive for "parent-declared protected day" already exists and is Holiday; the auto-freeze stays strictly the *automatic* emergency buffer. (User originated the "enter a freeze day like a lesson" framing; the refinement is that the per-day fact lands on `holidays[]`, not a new array.) Future hook noted but NOT built: an optional `kind` field on a holiday entry if Phase 6's calendar later wants to colour sick-days distinctly from trips — re-skinnable with no data migration.

**Other load-bearing spec decisions** (full detail in the spec): `parent.html` is a separate page with its own `parent.js` **module** entry — *not* an inline module script, because `deploy.sh` only cache-busts `from "./x.js"` inside `.js` files and `src="x.js"` inside `.html`, so an inline `import` would dodge the stamp and risk a stale module (the [[cf-pages-caches-js-4h]] gotcha). The PIN lives in its own `cello.parent` key, never in `cello.progress`, to keep the engine-input shape = the five fact arrays (same reasoning as the `cello.test` key). Date defaults read `store.effectiveToday()` so the test-panel offset and field-test stay consistent.

**Doc convention reinforced (by the user):** design docs describe the **current** implementation as a snapshot — written as if it were always this way. No "old X → new Y", "this replaces…", or "better than the previous approach" archaeology in `docs/`; that evolution lives in chronicles + git. On request, scrubbed the "this also covers the old 'grant a freeze'" framing from both the spec and the implementation roadmap. Applies to all future doc edits.
